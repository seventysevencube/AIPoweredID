# AIPoweredID planning audit — October 17, 2026

Status: independent, report-only review. **Every recommendation in this report is a proposal, not an approved requirement.** No existing planning document or prototype was changed. No provider, stack, application work, deployment, or contact with rights holders is selected or authorized by this report.

Audited baseline: `seventysevencube/AIPoweredID`, `main` commit `78f437dc466e58094483dfdddec1b818da97b682`. References and line numbers below refer to that revision. Scope: both README entry points, every current file in `docs/`, and every file in `prototypes/`; archive material was consulted only for superseded requirements. All external sources were checked **2026-10-17**; this is the access date unless another date is stated. Findings about missing controls concern planning omissions, not demonstrated vulnerabilities in an application that does not yet exist.

Method: read the current documents in precedence order; inspect the 14 standalone wireframes and their editable fragment definitions, rendered-text templates, state handlers, and handoff logic; verify all 28 manifest size/hash entries. The manifest matches all files. This is a source-level interaction/flow audit, not browser visual QA, a penetration test, an assistive-technology test, or legal clearance. Prototype limits and fictional sample facts were not treated as product requirements. Synced project sources were not modified.

## 1. Bottom line

**Not ready for a committed technical build plan.** The workflow is sufficiently developed to discuss architecture constraints, but five policy/contract gaps should be resolved or explicitly bounded before the plan becomes an implementation commitment:

1. Current rules are scattered across appended corrections; some actively worded instructions still contradict later approvals. A builder cannot reliably find one current rule without reading several files (B1).
2. Review, acceptance, snapshots, and upstream-change propagation lack a complete behavioral contract. Those choices determine the records and transactions the technical plan must support (B2).
3. The $20 cap has no admission/reservation rule for concurrent or already-running calls. Checking last reported spend cannot satisfy the approved policy (B3).
4. The intended data boundary, deletion/retention policy, and minimum guest/authentication controls remain unsettled. “No confidential organizational material” is inadequate as the sole privacy boundary (B4).
5. Six Boxes and Kirkpatrick are integral named product features without documented product-use clearance. Establish a permission or independently authored alternative path before committing to those screens (B5).

Recommendation: resolve the five contracts with a small decision addendum and approved canonical corrections, then write the technical plan. Full legal agreements, production prompts, exact page layouts, and measured quality results need not all exist before planning; they have explicit later release gates below. The deferred walkthrough remains deferred. This audit does not make completing that exercise a prerequisite for the technical plan.

The approved baseline has substantial strengths: explicit human decisions, conditional L2 gating, separate learning/nonlearning routes, source uncertainty, sample-first Development, non-AI exports, fixed shared versions, and unusually concrete autosave checks. The main problem is operational definition and breadth, not a lack of instructional-design thinking.

### Recommended state meanings and handoff rules

1. **Draft**: editable proposal/current working revision. Saving is allowed with gaps. **Needs review**: current revision has not been reviewed. **Reviewed**: a designer reviewed this exact revision, even if labeled issues remain. **Accepted**: explicit acceptance of a scoped proposal or exact handoff baseline; it does not make unsupported facts true. **Needs update**: a previously reviewed/accepted item depends on a changed input and must be reassessed. Track these dimensions separately rather than forcing mutually exclusive meanings into one dropdown. **Ready for handoff** is an artifact-level designer confirmation supported by required checks, not a synonym for Reviewed.
2. Generate Design from the explicitly selected saved Analysis revision, including an acknowledged incomplete baseline where permitted. Initial Six Boxes can establish L2 applicability. A learning route cannot enter instructional Design without identified, designer-confirmed L2; nonlearning needs N/A rationale; investigation holds drafting.
3. Draft Design substeps may carry review flags and gaps. Acceptance of the Development input must distinguish **structural sample with placeholders** from **written sample with verified essential sources/answers**. Sample treatment acceptance applies only to the sample's version and structure/style. New full-draft sections remain drafts; accepted sample edits survive.
4. Recommendation: any semantic change to a source, route, measure, objective, assessment, scope or tool invalidates linked current downstream review/readiness transitively. Presentation-only changes need an explicit whitelist and must not bypass factual checks. Show affected records and the reason; do not regenerate automatically. Unrelated sections keep their status. Earlier shared/exported snapshots keep original labels and content.
5. Recommendation: if an input changes while a job runs, save the result against its original baseline and mark it stale/proposed; do not apply it over a newer revision. Apply/reject/compare is explicit. Cancellation or page closure does not imply no bill; completed results are recoverable without rerunning.
6. Recommendation: Ready requires applicable sections reviewed at current revisions, integrated objective/task coverage, preserved Design-owned assessments, verified essential facts/answers, no unresolved essential source/tool/implementation issue, and explicit designer confirmation. Defined media placeholders and permitted L3/L4 unknowns can remain nonblocking. Acknowledgement alone cannot downgrade an essential issue.

Recommended contract tests: change one objective after Ready and during generation; change a source without changing its filename; switch nonlearning → learning → nonlearning; reorder/delete/merge an EO referenced by two assessments; use one assessment twice in a sequence; restore a prior draft; revoke a link to an older snapshot; and export that exact saved version. Assert preserved IDs/content, precise invalidation, old-comment traceability, no silent rewrite, and no incidental AI call.

### Recommended spending-control contract (B3)

1. Keep one authoritative shared ledger. Before dispatch, atomically admit only if **settled charges + outstanding conservative reservations + proposed reservation ≤ $20** for the defined month. Every designer, background quality check, repair and research subcall uses the same rule. No direct client-held provider key or bypass path.
2. A reservation covers bounded input, maximum billable output/reasoning, allowed tool/search calls and the operation's quality/recovery allowance. If the provider/tool cannot expose a bounded maximum, disable that operation near the cap or require a safer bounded alternative. Reserve enough for a complete chain, or clearly label generation-only partial completion and gate each later stage before dispatch.
3. Example: at $18.80 settled with no pending work, two $0.80 requests arrive simultaneously. Only one is admitted; the other sees $19.60 committed and is paused. Checking the balance twice without an atomic reservation admits both and can reach $20.40.
4. Settle actual billed usage once; release only confirmed unused reservation. Record rate/model version, idempotency key and each subcall. Failed/truncated calls can incur costs. An ambiguous timeout remains reserved until reconciled; retry must not duplicate a charge/result unknowingly. A crashed worker must not free a reservation simply because a timer elapsed.
5. If a chain cannot reserve the next check/repair/research call, stop **before that call**, save completed draft units as unreviewed/incomplete and explain what remains. Do not mark quality-pending output Ready. Preserve accepted work, manual editing, review/comments and non-AI exports.
6. Do not depend on canceling a stream exactly at $20: received usage can lag already-billed work. Bound at admission. If actual billing nevertheless exceeds a reservation because of a pricing/configuration error, stop further AI, reconcile and surface the incident; do not silently increase the approved cap.
7. Recommendation: account in USD, calendar month in America/Chicago, no carryover, with each in-flight job charged/reserved against its admission period until settled. Reconcile provider billing before claiming precise remaining balance. Warn at $16 settled spend and show a separate “committed including pending” early warning if reservations cross it. Show reset time and last reconciliation; keep hard-cap messaging honest about fees outside the AI pool.

Recommended tests: five concurrent designers; exactly $20; reservation fits but actual is lower; completion before retry/quality stage; timeout with unknown charge; duplicate delivery; price change; restart; midnight/month rollover; malformed model usage report; and zero-budget editing/export. These are behavioral requirements to decide, not a stack design.

### Recommendation: narrow web research for the pilot

**Recommendation: accept only URLs explicitly supplied/selected by the designer; defer autonomous open-web discovery.** This changes the current approved research option and needs approval. Do not silently treat the recommendation as existing scope.

Value remains: an authoritative public procedure or tool-capability reference can fill a specific gap. Ordinary search fees in this estimate are small; the harder costs are retrieval/token growth, checking whether passages support claims, maintaining provenance, rights to reuse material, and hostile page instructions. Search output is not a reviewed source merely because it has a citation.

Recommendation: use a small explicit URL count and fetch-size limit, public HTTP(S) pages only, no credentials/private-network addresses/automatic authenticated browsing, redirect checks and timeouts, no paywall bypass, and no link-following expansion. Keep URL, title, retrieval date, content revision/hash and supporting passage locator. Treat the content as untrusted reference data. Require claim-to-passage review for material facts and flag conflicting sources; do not copy large protected passages into learner deliverables. A supplied URL narrows discovery but does not remove prompt injection, network-request or copyright risk. These are recommendations informed by [OWASP prompt-injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) and [U.S. Copyright Office guidance](https://www.copyright.gov/what-is-copyright/), accessed 2026-10-17.

Defer open discovery until evidence shows it improves accepted output enough to justify verification effort. Recommendation: in a provided-material-only project, never fetch a URL or search implicitly; designer consent to a source-mode change and an explicit bounded action are required. The narrowed pilot can also use pasted, authorized excerpts when safe URL retrieval is unavailable.
